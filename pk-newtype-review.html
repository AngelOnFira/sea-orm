1. TL;DR

Both reviewers + adversarial tests agree: do not merge as-is. The feature works for the simple cases, but six SHOULD-FIX bugs are now reproducible (not theoretical) and one design opportunity was missed.

  • SHOULD-FIX   Multi-FK overwrite. Confirmed: when the same column is constrained against two parents, the second silently overwrites the first.
  • SHOULD-FIX   Wrapper naming. A table named cake_id produces CakeIdId; a composite PK with a column literally named id produces a wrapper named Id.
  • SHOULD-FIX   Type-alias regression. type LegacyUserId = i32; pub id: LegacyUserId; silently flips from autoincrement-true to autoincrement-false.
  • SHOULD-FIX   Stale entity files on regen. Dropping a table leaves its .rs on disk.
  • SHOULD-FIX   --with-pk-newtypes --with-serde both generates code that does not compile: the wrapper has no Serialize/Deserialize.
  • SHOULD-FIX   find_by_id tightening is a universal breaking change. Confirmed by adversarial test: find_by_id(1u8) / find_by_id(1i64) no longer compile.
  • DESIGN   Single generic Id<E> would have delivered the same safety with one type, automatic blanket impls, and zero per-table codegen.

Self-referential safety is weak — user_follower(user_id, follower_id) still lets you swap arguments at the call site. BUT there's a clean fix using per-column "role" newtypes — see §7.

UUID PK newtype round-trip actually works. Adversarial test added a real DB round-trip and it passes. Coverage gap closed.

Migration-type leakage concern does NOT apply — entities are regenerated snapshots, not append-only history. Detailed in §5.

2. Using a typed foreign key — sample code

With --with-pk-newtypes applied to a parent (cake) and a child (fruit), the generated entities look like this:

// examples/basic/src/entity/cake.rs
use sea_orm::entity::prelude::*;

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash, DeriveValueType)]
pub struct CakeId(pub i32);

#[sea_orm::model]
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel)]
#[sea_orm(table_name = "cake")]
pub struct Model {
    #[sea_orm(primary_key, auto_increment)]
    pub id: CakeId,
    #[sea_orm(column_type = "Text", nullable)]
    pub name: Option<String>,
    #[sea_orm(has_many)]
    pub fruits: HasMany<super::fruit::Entity>,
}

// examples/basic/src/entity/fruit.rs
use sea_orm::entity::prelude::*;

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash, DeriveValueType)]
pub struct FruitId(pub i32);

#[sea_orm::model]
#[sea_orm(table_name = "fruit")]
pub struct Model {
    #[sea_orm(primary_key, auto_increment)]
    pub id: FruitId,
    pub name: String,
    pub cake_id: Option<super::cake::CakeId>,   // ← typed FK
    #[sea_orm(belongs_to, from = "cake_id", to = "id")]
    pub cake: HasOne<super::cake::Entity>,
}

Pattern A — one-shot fetch with the loader (preferred)

async fn describe_fruit(db: &DbConn, id: fruit::FruitId) -> Result<(), DbErr> {
    let loaded = fruit::Entity::load()
        .filter_by_id(id)                  // only accepts FruitId — compile error if you pass CakeId
        .with(cake::Entity)              // eager-loads the parent cake via the belongs_to relation
        .one(db)
        .await?
        .expect("fruit not found");

    match loaded.cake {
        HasOne::Loaded(cake) => println!("{} grows on the {} cake", loaded.name, cake.name.unwrap_or_default()),
        HasOne::Unloaded          => unreachable!(),
    }
    Ok(())
}

Pattern B — manual two-step using the typed FK column

The FK column is already a CakeId, so you pass it straight to find_by_id on the parent — no wrapping, no casting:

async fn cake_of(db: &DbConn, fruit_id: fruit::FruitId) -> Result<Option<cake::Model>, DbErr> {
    let fruit = fruit::Entity::find_by_id(fruit_id).one(db).await?;
    let Some(fruit) = fruit else { return Ok(None); };

    match fruit.cake_id {
        Some(cake_id) => cake::Entity::find_by_id(cake_id).one(db).await,
        None          => Ok(None),
    }
}

Pattern C — the safety win, demonstrated

let cake_id   = cake::CakeId(7);
let fruit_id  = fruit::FruitId(3);

cake::Entity::find_by_id(cake_id).one(db).await?;       // ok

cake::Entity::find_by_id(fruit_id);                  // expected CakeId, found FruitId
cake::Entity::find_by_id(7_i32);                     // expected CakeId, found i32

Pattern D — reverse direction (has_many)

async fn cake_with_fruits(db: &DbConn, id: cake::CakeId) -> Result<_, DbErr> {
    let cake = cake::Entity::load()
        .filter_by_id(id)
        .with(fruit::Entity)         // loads all fruits whose cake_id == this cake.id
        .one(db)
        .await?
        .expect("cake not found");

    for fruit in cake.fruits.unwrap_or_default() {
        println!("{:?} -> {}", fruit.id, fruit.name);
    }
    Ok(())
}

3. Why we ended up tracking ref_table, ref_column, current_table, pk_newtype_index

The core problem

Codegen receives a list of entities, each with a list of Columns. For a Column to render its Rust type as super::cake::CakeId instead of i32, three pieces of information have to be available at the moment Column::get_rs_type is called:

  1. Is this column's table's PK wrapped under --with-pk-newtypes? → it needs to look itself up by (my_table, my_column_name) and emit the local newtype.
  2. Is this column a foreign key, and if so, to which (parent_table, parent_column)? → it needs to look up that key and emit super::ref_table::RefTableId.
  3. What is "my table"? → Column alone doesn't know which entity it belongs to.

Where each piece lives

PieceLives onPopulated whenWhy
ref_table
ref_column		 Column
(per-column)		 EntityTransformer::transform walks each BelongsTo relation and writes them back So a column knows "I point at those columns over there." Needed for piece (2).
pk_newtype_index ColumnOption
(per-render)		 Built once in EntityWriter::write_entities before any entity is rendered The shared (table, column) → Ident lookup so any FK resolution returns the same identifier name the parent table is going to emit.
current_table ColumnOption
(per-render)		 Set per-entity by column_option(entity, …) Without it, a column doesn't know whether (my_name) is a PK in its own table or just a coincidentally-named column.

"But can ref_table be more than one?"

Yes — and adversarial test #1 confirms it's a real bug. Two cases:

Case A — composite FK (handled)

A single FK constraint spans multiple columns pointing at a multi-column PK. Example: FOREIGN KEY (a, b) REFERENCES parent(x, y). The code iterates columns.iter().zip(ref_columns.iter()) within one relation — each child column gets paired with its corresponding parent column. Correct.

Case B — same column in 2 FKs (BROKEN)

A single column constrained twice against two different parents:
user_id INT,
FOREIGN KEY (user_id) REFERENCES users(id),
FOREIGN KEY (user_id) REFERENCES legacy_users(id);

Legal SQL. Two Relation entries are produced. The current loop in transformer.rs:132-141 overwrites col.ref_table on each iteration → the last FK wins silently. Codegen will emit a wrapper from the wrong parent.

Fix: change to Vec<(String, String)> and either error or pick a documented winner under --with-pk-newtypes.

4. Should find_by_id have been feature-flagged?

Yes — both reviewers and adversarial test #8 confirm the call was wrong. The tightening (find_by_id<T: Into<ValueType>> → find_by_id(ValueType)) breaks universally but benefits only callers who also adopt the newtype codegen.

OptionBehaviorTrade-off
Keep Into<ValueType> lenientStatus quo. Safety by convention.Zero breakage but trybuild test #2 regresses if a user adds an innocent From<i32>.

5. Migration-type leakage — does the same problem apply here?

Verdict: NO. The SeaORM team's concern was structural to migrations (append-only history). It doesn't apply to entity newtypes.

The original concern

Migrations reference column types. Migrations are append-only — frozen the moment they ship. If migration #3 references a type defined alongside an entity, and migration #57 drops the column/table, the historical migration would reference a now-deleted type. Migration history would no longer compile.

Why entity newtypes are different

  1. Entities are a regenerated snapshot, not history. Codegen walks the current live schema on every run. No append-only frozen artifact.
  2. Migrations don't reference entity types. Searches across sea-orm-migration/ show migrations only touch ColumnType, ColumnDef, Iden, Table. When migrations need queries, the pattern is local mini-entity redefinition inside the migration module.
  3. Regen on a dropped table = wrapper disappears. Drop users, regen — no more UserId. Business code referencing UserId gets loud compile errors pointing exactly at the fix sites.
  4. The wrapper is transparent at SQL/wire level. DeriveValueType on UserId(i32) delegates column_type() → ColumnType::Integer. SQL knows nothing about the wrapper.

Adjacent risk: stale .rs files on disk

Adversarial test #12 confirms: when you drop a table and regenerate, mod.rs and dependent .rs files are updated, but the orphaned a.rs stays on disk. Pre-existing codegen behavior, not unique to newtypes — but it does mean the newtype declaration lingers in source control until manually deleted.

6. GitHub discussion #1310 — original proposal vs what we built

The discussion (github.com/SeaQL/sea-orm/discussions/1310, December 2022 → July 2023) is short — one OP, two maintainers, eight comments. The opener was AngelOnFira (the user driving this branch). Here's what was actually said and how the current implementation matches up.

The original problem statement (Dec 2022)

"In this model, I'm storing a few things:
— The literal discord_id that I would get from this object
— A guild_id, which isn't actually the id of a Discord Guild, but instead the id of a row in another table
— A channel_id, which is also a pointer to somewhere else in the database.

So in this case, when I get this model from the database, it's up to me as the developer to remember which of those are Discord IDs, and which are IDs of Database rows." — AngelOnFira, OP

The original user pain wasn't "PostId vs CakeId" — it was "external system ID (Discord, Stripe, ...) vs database row ID". Per-table wrappers (UserId(i32)) do solve cross-table confusion, but they don't fully solve the original framing where the same physical column is a "pointer to external system" rather than "pointer to another row." The OP's proposed solution included that case:

pub struct DatabaseId(pub i32);
pub struct DiscordId(pub i32);

pub struct Model {
    pub id: i32,
    pub discord_id: DiscordId,         // external-system marker, not an FK
    pub guild_id: Option<DatabaseId>,  // pointer to another row
    pub channel_id: DatabaseId,        // pointer to another row
}

Maintainer response (Dec 2022)

"I guess we can start by providing an easier interface to use custom type (newtype) in SeaORM model. [proposed manual impl From<T> for Value / TryGetable / ValueType]. A derive macro can implement all these traits on behalf of the user." — billy1624, maintainer
"+1 for this"— tyt2y3, maintainer

The maintainer's response is exactly what DeriveValueType later became. The macro layer already shipped — that's why our Phase 1/2 work could lean on it.

OP's codegen extension (July 2023)

Seven months later the OP returned with a codegen-specific proposal — but he proposed a type alias, not a newtype:

pub type ChallengeTablePK = i32;

"It could be quite helpful to get codegen to generate a custom type for the primary key. It could be an opt-in flag when generating entities." — AngelOnFira

Critically important observation: a type alias gives zero compile-time safety. type ChallengeTablePK = i32; is transparent. fn(challenge_id: ChallengeTablePK) and fn(raw: i32) accept the same values. Our implementation (newtypes) actually delivers what the OP wanted, not what the OP proposed. That's a strict improvement.

OP on naming convention

"I imagine that since tables can't have the same name, it shouldn't be too hard to just use that. … maybe it could just be named something generic like TablePK?" — AngelOnFira (re unary PK)
"pub type CakeFillingPkCakeId = i32;
pub type CakeFillingPkFillingId = i32;

Their field names should still keep them unique … I think it needs to include both the table name and the field name as an identifier, without either becoming truncated so that there aren't any discrepancies if names are changed." — AngelOnFira (re composite PK)

The OP's naming convention is more verbose than ours but avoids the collisions we ship with. Compare:

Where the OP's convention is better

The "<Table>Pk<Field>" pattern would have automatically caught the self-ref junction bug. Generating UserFollowerPkUserId and UserFollowerPkFollowerId as distinct types means a swap fails to compile. Our implementation chose the more elegant-looking "reuse parent PK type" approach, which gives cross-entity safety but loses positional safety inside the junction.

Where our implementation is better

Cross-entity composite confusion is much more common than positional junction swaps. If you have cake_filling.cake_id: super::cake::CakeId, you can pass cake.id into a function expecting cake_filling.cake_id directly, no conversion. With the OP's verbose convention you'd need to convert: CakeFillingPkCakeId::from(cake.id.0). Trade-off: cross-entity reuse vs intra-junction positional safety.

Things never raised in #1310

  • Tightening find_by_id's signature. Not mentioned. Unilateral design call in our branch.
  • Migration-type leakage. Not mentioned in this thread. (You said you'd discussed it elsewhere.)

The OP's <Table>Pk<Field> pattern, ironically, would have caught one of the bugs adversarial review later found.

7. Role newtypes for same-type junctions — your idea, expanded

You asked:

"Couldn't we just have a type wrapper in that entity that disambiguates the two columns, but this type is just labelled and equal to the type that both are?"

Yes — and it's the right idea. Let me sketch what this looks like concretely.

The problem, restated

Current codegen output for the self-ref junction:

// user_follower.rs — current output
pub struct Model {
    #[sea_orm(primary_key, auto_increment = false)]
    pub user_id: super::user::UserId,
    #[sea_orm(primary_key, auto_increment = false)]
    pub follower_id: super::user::UserId,
}

Both fields share UserId. Adversarial test #6 proves: find_by_id((follower.id, user.id)) compiles. Swapped arguments → silent wrong row.

The role-newtype fix

For self-ref junctions only, codegen emits per-column "role" wrappers around the parent PK type:

// user_follower.rs — proposed role-newtype output
use sea_orm::entity::prelude::*;

// These two wrappers are structurally identical — both hold a UserId —
// but the type system treats them as distinct.
#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash, DeriveValueType)]
pub struct FollowedId(pub super::user::UserId);

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash, DeriveValueType)]
pub struct FollowerId(pub super::user::UserId);

#[sea_orm::model]
#[sea_orm(table_name = "user_follower")]
pub struct Model {
    #[sea_orm(primary_key, auto_increment = false)]
    pub user_id: FollowedId,    // the user being followed
    #[sea_orm(primary_key, auto_increment = false)]
    pub follower_id: FollowerId,  // the user doing the following
}

Now the same swap from before fails to compile:

user_follower::Entity::find_by_id((user_a.id, user_b.id));
//                                        ^^^^^^^^^^  ^^^^^^^^^^
//                                        UserId      UserId
// expected (FollowedId, FollowerId), found (UserId, UserId)

// You have to be explicit about the role:
user_follower::Entity::find_by_id((
    FollowedId(user_a.id),
    FollowerId(user_b.id),
)).one(db).await?;

When to emit role wrappers

The codegen rule would be: whenever a single table has >1 FK column pointing at the same parent PK, generate a per-column role wrapper for those columns rather than reusing the parent PK type directly. Examples:

  • user_follower(user_id, follower_id) — both FK to users.id → emit FollowedId + FollowerId.
  • friendship(a, b) — both FK to users.id → emit role wrappers based on column names.
  • edge(source, target) in a DAG — both FK to node.id → emit SourceId + TargetId.

For the common case (single FK, e.g. fruit.cake_id → cake.id), the current behavior (reuse parent's CakeId) stays — no extra wrapper needed.

How the wrapper relates to the parent type

Two equally-valid implementations:

Option A: nested newtype (shown above)

pub struct FollowerId(pub UserId);

Holds the parent wrapper. .0 gets you back to the UserId. DeriveValueType already supports this — it delegates everything to the inner type, so column-type, SQL serialization, TryFromU64 all work transparently.

Option B: direct inner

pub struct FollowerId(pub i32);

Holds the raw scalar. From<UserId> and From<FollowerId> for UserId impls let users convert explicitly. More verbose at call sites but lighter on type machinery.

Option A is better — it composes cleanly with DeriveValueType's existing delegation, and the user can write follower.user_id.0 to get a UserId.

Why this is a meaningful upgrade

Self-ref junctions are the worst class of bug in this domain. They produce semantically-wrong rows with no DB-side complaint (the FK constraint accepts both directions). A code reviewer rarely catches the swap because both arguments are named user_id-shaped. Compile-time role enforcement turns a silent-wrong into a loud-wrong. This is the highest-leverage extension to the feature.

Cost

Roughly 50 lines in EntityWriter::build_pk_newtype_index to detect the same-parent-multiple-FKs case, plus tweaks to Column::get_rs_type to emit role wrappers in that case. The trybuild fixture is the same shape as the existing ones. No breaking change.

8. Deep-dive: Id<E> phantom-typed alternative

The reviewer claimed our per-table-struct approach is "the obvious-but-not-best translation" and that a single generic Id<E> would have been cleaner. Here's what that means in full.

What "phantom type" means

Rust has std::marker::PhantomData<T> — a zero-sized type parameter that exists only at the type level. It lets you parameterize a struct by a type you don't actually store. The classic use: making structurally-identical types distinct.

An Id<E> is a wrapper around the entity's PK value, parameterized by the entity it belongs to. Id<cake::Entity> and Id<fruit::Entity> have the same memory layout (both are i32 at runtime) but are different types at compile time.

The basic shape

// In sea-orm core:
use std::marker::PhantomData;

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
pub struct Id<E: EntityTrait> {
    pub value: <E::PrimaryKey as PrimaryKeyTrait>::ValueType,
    _phantom: PhantomData<E>,
}

impl<E: EntityTrait> Id<E> {
    pub const fn new(value: <E::PrimaryKey as PrimaryKeyTrait>::ValueType) -> Self {
        Self { value, _phantom: PhantomData }
    }
}

The _phantom: PhantomData<E> field is zero-sized at runtime — it disappears entirely. But to Rust's type checker it makes Id<cake::Entity> a fundamentally different type from Id<fruit::Entity>, even though both wrap an i32.

What user code looks like

use sea_orm::{Id, entity::prelude::*};

let cake_id: Id<cake::Entity> = Id::new(7);
let fruit_id: Id<fruit::Entity> = Id::new(3);

cake::Entity::find_by_id(cake_id).one(db).await?;       // ok
cake::Entity::find_by_id(fruit_id);                  // expected Id<cake>, found Id<fruit>

Same compile-time safety as our newtypes. But there's no per-entity struct definition required — every entity automatically has a type-safe ID just by being an EntityTrait.

What changes about codegen

Almost nothing. The model struct just changes from pub id: i32 to pub id: Id<Entity>. No standalone wrapper struct to emit, no build_pk_newtype_index, no gen_pk_newtype_decls. FK columns become pub cake_id: Id<super::cake::Entity>.

Why it's better

  • One type to derive on, one type to teach. All the blanket impls (Clone, Copy, Debug, Hash, Display, Serialize, Deserialize, ts_rs::TS) are written once in sea-orm core and apply to every entity for free. Compare: with our newtypes, every wrapper has its own derive list and adversarial bug #5 happens because we forgot one.
  • Zero codegen surface. No --with-pk-newtypes flag needed. The whole feature collapses to "use Id<Entity> in your model field."
  • Zero collision risk. The wrapper isn't a named type per table. A cake_id-named table doesn't produce CakeIdId; it produces Id<cake_id::Entity>. No naming bugs possible.
  • Composite PKs are clean. Id<cake_filling::Entity> holds (i32, i32) as its inner — still type-distinct from Id<other_junction::Entity> even though both wrap the same tuple. No per-column code to generate.
  • Serialize/Deserialize are blanket-derived once. When the inner ValueType is serializable, Id<E> transparently serializes as that value: 
    #[cfg(feature = "with-serde")]
impl<E: EntityTrait> Serialize for Id<E>
where <E::PrimaryKey as PrimaryKeyTrait>::ValueType: Serialize
{
    fn serialize<S: Serializer>(&self, s: S) -> Result<S::Ok, S::Error> {
        self.value.serialize(s)
    }
}
    This single block fixes adversarial bug #13 for every entity in the world. Our current per-table newtype design can't do that — each wrapper needs its own derive.
  • JSON wire format stays identical. Id<cake::Entity> serializes as just 7, not {"value": 7}. Same on the input side.
  • The whole feature ships as a library type, not a CLI flag. Existing entities can opt in by changing one field's type.

The downsides of Id<E>

  • The type name is verbose at use sites. Id<cake::Entity> vs CakeId. Function signatures get longer: 
    async fn lookup_cake(id: Id<cake::Entity>) -> Cake { ... }
// vs
async fn lookup_cake(id: cake::CakeId) -> Cake { ... }
    Mitigation: a one-line type alias in the entity module gives you the best of both worlds: 
    pub type CakeId = sea_orm::Id<Entity>;
    This alias is trivial codegen — one line per entity, vs an entire struct definition with derives.
  • Cross-entity conversion patterns differ. With our newtypes, FK fields are the parent's type directly: pub cake_id: super::cake::CakeId. With Id<E>, FK fields are pub cake_id: Id<super::cake::Entity>. Functionally equivalent — just longer at the source. With the alias trick, you can write pub cake_id: super::cake::CakeId and it's still Id<cake::Entity> under the hood.
  • Self-ref junction role-newtype problem is harder. You can't have Id<user::Entity, FollowerMarker> easily — adding a second phantom slot ripples through every API that takes Id<E>. The per-table struct approach is more flexible here. So if role newtypes (§7) are a goal, the codegen-struct path is actually better-suited.
  • Existing entities can't easily migrate. A codebase already using pub struct UserId(pub i32); would have to change every UserId to Id<user::Entity>. Newtypes can be added as gradual additions.
  • Documentation footprint. Id<E> needs its own dedicated docs page explaining phantom-typed wrappers, blanket impls, etc. Per-table newtypes are more discoverable because they show up in the entity module's namespace.

Why we didn't take this path

Honest answer: I followed the existing trail. The OP's #1310 proposal said "per-entity wrapper type." DeriveValueType was already in place. The path of least resistance was per-table structs.

If we were starting from scratch with no prior art, Id<E> is probably the better core design and per-table aliases (pub type CakeId = Id<Entity>;) are the right ergonomic veneer. The role-newtype case (§7) is the one area where named structs win, and codegen could emit role wrappers on top of the Id<E> base for junction tables specifically.

The hybrid design (best of both)

A v2 of the feature could combine all three:

  1. Core: sea_orm::Id<E> as a library type with blanket impls.
  2. Ergonomic veneer: codegen emits pub type CakeId = Id<Entity>; per entity. One-line alias, no collision possible.
  3. Role layer: for self-ref junctions, codegen emits standalone wrapper structs (FollowedId, FollowerId) on top of the Id<E> core. Distinct types per role.

This design gives you every win:

  • Cross-entity safety from the phantom parameter ✓
  • Free blanket impls (Serialize, Display, Copy) ✓
  • Ergonomic short names (CakeId, not Id<cake::Entity>) ✓
  • Positional safety inside self-ref junctions ✓
  • Zero naming-collision risk on the core (only the role wrappers have to worry about it) ✓

Net design verdict: a future v2 of this feature should start with sea_orm::Id<E>, generate per-table type CakeId = Id<cake::Entity>; aliases for ergonomics, and emit standalone role-newtype structs for self-ref junctions. That's the design we'd ship if we had the chance to do it again.

9. Detailed findings with worked examples

This section expands every reviewer concern with a concrete scenario, so it's clear how each one comes up in practice — not just as an abstract risk.

Finding 1 — Multi-FK column overwriteSHOULD-FIX

What it is

A single SQL column can be constrained against two different parent tables in the same CREATE TABLE. This is legal SQL — both FKs must hold for any inserted value. Our codegen models per-column FK back-references with a scalar Option<String>, so when the transformer walks the relations, the second FK silently overwrites the first.

When it comes up in practice

The most realistic case is a data migration period where a system is moving from one parent table to another, but the old constraint is left in place for safety. Example: you're migrating from legacy_users(id) to users(id). During the transition, a child table might validly carry both FKs:

CREATE TABLE session (
    id INTEGER PRIMARY KEY,
    actor_id INTEGER NOT NULL,
    FOREIGN KEY (actor_id) REFERENCES users(id),
    FOREIGN KEY (actor_id) REFERENCES legacy_users(id)
);

If you generate entities with --with-pk-newtypes against this schema, codegen will pick one parent and emit a wrapper from it. Whichever loses is a silent type confusion — code that tries to assign session.actor_id to a function expecting the lost type fails at runtime in unpredictable ways.

Less common but more dangerous

A more practical reason this shows up: some ORMs and migration tools emit duplicate FK constraints when the user runs multiple migrations that all add the same constraint. The database accepts duplicates as long as the columns/names differ. Codegen sees both and silently picks one.

Fix

Change Column::ref_table from Option<String> to Vec<(String, String)>. Under --with-pk-newtypes, either error out ("ambiguous — please disambiguate") or pick a documented winner (first-by-name) and emit a comment in the generated code.

Finding 2 — <Table>Id wrapper naming has degenerate edge casesSHOULD-FIX

What it is

Codegen generates the wrapper name as format!("{}Id", table_camel) for unary PKs, or uses the column-camel-case verbatim when the column ends in "Id" (composite PKs). Edge cases:

  • Table ending in _id: cake_id → wrapper CakeIdId
  • Composite PK with column literally named id: wrapper named Id (collides with sea_orm::Id if it ever ships, and is a generic-sounding name that's painful to read)
  • Composite PK with column ending in Id: wrapper reuses the camel name; tag_id → TagId globally, which could collide with a different table's wrapper

When it comes up in practice

Tables ending in _id are common in junction/lookup tables. Examples:

  • session_token_id — a lookup table mapping session ids to token ids
  • discord_id_to_user_id — an integration mapping table
  • external_account_id — a table whose primary entity is itself an ID

The id-named-column-in-composite case is even more common. Picture a junction table with two PK columns:

CREATE TABLE association (
    id INTEGER,
    secondary_id INTEGER,
    PRIMARY KEY (id, secondary_id)
);

Codegen produces pub struct Id(pub i32) and pub struct SecondaryId(pub i32) inside mod association. A bare Id identifier at the module-top level is awful: it collides with anything anyone might glob-import as Id, including a hypothetical sea_orm::Id<E>.

Fix

The OP's #1310 convention solved this — always prefix with the table name: AssociationId, AssociationSecondaryId. Slightly verbose but no collisions.

Finding 3 — Auto-increment heuristic regression on type aliasesSHOULD-FIX

What it is

Phase 2 replaced the suffix denylist (String, Uuid) with a positive allowlist of literal integer type names (i8/i16/i32/.../usize). The check is purely textual — it sees the post-quote!{#ty} string. So type LegacyUserId = i32; pub id: LegacyUserId; sees the text "LegacyUserId" and defaults auto_increment = false, even though the underlying type is i32.

When it comes up in practice

Anyone using type aliases for documentation hygiene. This is a real Rust pattern:

// in some shared types crate
pub type UserId = i32;
pub type TenantId = i64;

// in the entity
#[sea_orm(primary_key)]
pub id: UserId,    // previously: auto_increment defaulted true
                  // now: auto_increment defaults false — silent regression

The runtime consequence: the user's INSERT statements used to omit the PK column and let the DB assign one. After regen, the macro emits no auto_increment in the entity's column def. Schema sync (if the user uses entity-first workflow) will now generate a non-autoincrement column. Or, if the DB column is already autoincrement, the entity's understanding of it desyncs from the DB.

The CLI sidesteps this because it explicitly emits auto_increment on the codegen output. But hand-written entities that previously used type aliases break silently.

Fix

Macros can't resolve type aliases (no type info at macro time), so the heuristic has to be textual. Two options:

  1. Restore the suffix denylist as a fallback: if the type name doesn't appear in the allowlist and doesn't end in "String"/"Uuid", default to autoincrement. Less aggressive about type-alias deprecation but preserves the common pattern.
  2. Emit a compile_error! when a PK type name doesn't appear in the allowlist, with a hint: "if your PK type is an integer alias, please add #[sea_orm(primary_key, auto_increment)] explicitly."
Finding 4 — find_by_id tightening blast radiusSHOULD-FIX

What it is

The old signature was find_by_id<T: Into<ValueType>>(values: T). The new signature is find_by_id(values: ValueType). The Into bound let callers pass any integer that could coerce into the PK type — find_by_id(1u8) worked because u8: Into<i32>.

When it comes up in practice

Anywhere ID values come from a different width than the PK's storage type. Examples:

  • API handlers parsing path parameters as u32 (URL convention) but storing as i32 (signed-integer DB column)
  • Counters or sequence values held as u64 being passed to a query against an i64-PK table
  • Test fixtures using bare integer literals like find_by_id(1) — adversarial test confirms bare literals still infer correctly, but explicit 1_i64 against an i32 PK now breaks

Adversarial test result

    |
18  |     cake::Entity::find_by_id(1u8);
    |     ------------------------ ^^^ expected `i32`, found `u8`

Fix

Three workable paths, ranked:

  1. Revert universal tightening, add find_by_id_strict. Best option: zero breakage, both signatures available, codegen-newtype docs recommend the strict form.
  2. Keep tightening, accept the breakage. Cleanest API surface but users get punished for not opting in to the new feature.
  3. Cargo feature flag. Worst option due to Cargo feature unification — a single non-opting transitive dep drags everyone back to lenient.
Finding 5 — --with-pk-newtypes --with-serde generates non-compiling codeSHOULD-FIX

What it is

Under --with-serde both, the Model gets derive(Serialize, Deserialize). But the PK wrapper struct does NOT — its derive list is hardcoded to (Clone, Debug, PartialEq, Eq, Hash, DeriveValueType). The result: the Model fails to compile because its field type doesn't implement Serialize.

Adversarial test result

error[E0277]: the trait bound `FooId: serde::Deserialize<'de>` is not satisfied
  --> src/foo.rs:9:5
   |
 9 |     pub id: FooId,
   |     ^^^^^^^^^^^^^ the trait `Deserialize<'de>` is not implemented for `FooId`

When it comes up in practice

Anyone using SeaORM with a JSON API surface. --with-serde both is the recommended flag for full-stack Rust+TypeScript projects. The combination just doesn't work today.

Fix

Propagate the --with-serde derives to the wrapper struct in gen_pk_newtype_decls. Trivial fix in EntityWriter. Also propagate --ts-rs when that feature exists. Note: the Id<E> design in §8 makes this problem disappear entirely — a single blanket impl in sea-orm core handles all entities.

Finding 6 — Stale .rs files on dropped tablesSHOULD-FIX

What it is

When a table is dropped and entities are regenerated, the codegen:

  • Rewrites the dependent entities' FK columns back to raw types ✓
  • Removes the deleted table from mod.rs ✓
  • Leaves the orphan .rs file on disk ✗

When it comes up in practice

A normal evolutionary workflow: developer drops legacy_users in a migration, regenerates entities. The new mod.rs doesn't list pub mod legacy_users, so the file is unreachable from main.rs — but it's still in the repo. On the next regen if anyone re-adds a same-named table, the old file gets overwritten partially, leaving stale wrapper definitions.

This is a pre-existing codegen behavior, not introduced by newtypes. But newtypes make it more visible because the wrapper structs (which a user might reference from business logic outside the entity tree) lingered without indication.

Fix

Either delete orphan files explicitly during regen, or write a clear comment at the top of generated mod.rs listing the tables that were dropped on this run.

Finding 7 — Same-type self-ref junctions don't catch swapsSHOULD-FIX

What it is

See §7 above. Both columns of a self-ref junction get the same parent PK type (UserId), so calling find_by_id((a, b)) versus find_by_id((b, a)) typechecks both ways.

When it comes up in practice

Self-referential junction tables exist in many domains:

  • Social: user_follower, friendship
  • Org charts: employee_manager
  • Permissions: role_inherits_from_role
  • Graphs/DAGs: edge(source, target)
  • Family trees: parent_child, partnership

The wrong-direction bug shows up when you fetch or insert a relationship row using arguments in the wrong order. The DB constraint accepts both directions (both columns reference the same table). There's no error from the DB and no warning from the type system. The user sees wrong-shaped data and has to debug from the user-visible symptom backwards.

Fix

Role newtypes per §7. ~50 lines of codegen, no breaking change, clean addition.

Finding 8 — Wrapper struct doesn't derive Copy on codegen outputNICE-TO-HAVE

What it is

The hand-edited adoption examples (in examples/basic/src/entity/cake.rs) include Copy in the derive list. The codegen output (from EntityWriter::gen_pk_newtype_decls) does NOT include Copy. This is a divergence between dogfooded code and what users will get.

When it comes up in practice

Any business code that holds an ID variable and passes it to multiple functions. Without Copy, every pass-through requires .clone():

let id = cake::CakeId(7);
cake::Entity::find_by_id(id).one(db).await?;       // moves id
let related = fruit::Entity::find().filter(...);
println!("{:?}", id);  // borrow of moved value

Workaround is just let id = cake::CakeId(7); cake::Entity::find_by_id(id.clone()) — annoying noise that breaks the "ids are just like numbers" mental model.

Fix

When the inner type is Copy (integer types, UUID, etc.), emit Copy in the wrapper's derive list. Simple type-name check in codegen.

Finding 9 — Wrapper struct doesn't derive DisplayNICE-TO-HAVE

What it is

Display is not derived. Anyone wanting to format an ID for logs has to use {:?} (which produces CakeId(7) instead of just 7) or write a manual impl.

When it comes up in practice

Logging. Tracing spans. URL path generation. JSON error messages. These all want the inner value, not CakeId(7):

tracing::info!(cake_id = ?id, "cake fetched");     // emits "cake_id=CakeId(7)" — verbose, wrong-looking
tracing::info!(cake_id = %id, "cake fetched");     // error: Display not implemented

let url = format!("/cakes/{}", cake_id);          // error: Display not implemented
let url = format!("/cakes/{}", cake_id.0);        // works but leaks the wrapper

Fix

Either auto-derive Display when the inner type is Display, or add a --with-pk-newtypes-display flag, or generate a manual impl Display when the inner is a known display-able type.

Finding 10 — strip_optional is a string round-tripNICE-TO-HAVE

What it is

In EntityWriter::gen_pk_newtype_decls, we need the bare inner type for the wrapper declaration (the wrapper holds i32, not Option<i32>, even if the column is theoretically nullable). The implementation serializes the TokenStream to a string, searches for "Option<", strips it, and parses back.

Why it's brittle

TokenStream::to_string() formatting is not API-stable across proc-macro2 versions. If a user shadowed Option or aliased it (unusual but legal), the substring match would fail or false-positive. The unwrap_or(ts) fallback silently hides any error.

When it would actually bite

Realistically? Rarely. PK columns are never NULL so the Option wrap never happens for them in real schemas. The code path is defensive — it'd matter only if a future codegen change started wrapping more aggressively.

Fix

Have Column::get_rs_type take an emit_optional: bool flag, and call it with false when emitting the wrapper. No post-hoc parsing needed.

Finding 11 — Rc<HashMap> vs ArcOUT-OF-SCOPE

What it is

PkNewtypeIndex is wrapped in Rc. The reviewer flagged this might be a problem if codegen is ever called from a multi-threaded context.

Why it's actually fine

proc_macro2::TokenStream is !Send. Codegen is fundamentally single-threaded — there's no async server tooling case where this matters. Rc is the right choice.

Fix

Add a comment in writer.rs explaining why Rc over Arc is intentional. No code change needed.

Finding 12 — Cross-entity bug class is narrow but realDESIGN

What it is

The headline benefit — "type-safe IDs prevent cross-entity confusion" — is real but narrow. Variable names usually catch find_by_id(post_id) on a user::Entity at code review. The actual class of bug newtypes catch best is:

  1. Function parameters where both types are i32: fn revoke_session(user_id: i32, session_id: i32) — swapping the arguments at the call site is silent. With newtypes (UserId, SessionId) it's caught at compile.
  2. Multi-PK tuples with distinct columns: find_by_id((post_id, tag_id)) vs find_by_id((tag_id, post_id)) — caught when the types differ.
  3. Refactor blast radius: when you change a function from accepting "the cake id" to "the fruit id", every caller has to update or get a compile error.

Industry comparison

LanguageApproachCost
TypeScriptBranded types: type UserId = number & { __brand: 'User' }Zero runtime cost, no constructor noise
Diesel (Rust)Convention only — user writes pub struct UserId(pub i32) themselvesNo codegen, user friction
HaskellPhantom-tagged: Id User, Id PostOne generic type, blanket impls free
SeaORM (us)Per-entity newtype struct via codegenReal safety + many small structs

Verdict

Not best-in-class but workmanlike. See §8 (Id<E>) for the better design we missed.

Finding 13 — Composite PK has no tuple-level wrapperDOC-ONLY

What it is

Composite PKs use per-column newtypes (e.g. cake_filling has cake_id: CakeId, filling_id: FillingId) but the ValueType is still a tuple (CakeId, FillingId). There's no single CakeFillingPk type to thread through APIs.

When it comes up in practice

Junction-heavy domains. If you want a function fn delete_link(id: cake_filling::CakeFillingPk), you have to write fn delete_link(id: (CakeId, FillingId)) instead. Works fine but slightly less ergonomic, and "the PK of a junction row" doesn't have a name you can use in docstrings.

Verdict

Document the pattern. Composite-PK wrappers could be added later without breaking change.

12. Bottom line

Don't merge the current branch as-is. Worth shipping after the fixes above.

The feature does what was advertised — cross-entity ID confusion is caught at compile time, UUID PKs work end-to-end, the trybuild harness pins the safety contract. The migration-type leakage concern doesn't apply. The original discussion #1310 asked for less than what we delivered (the OP proposed type aliases; we shipped real newtypes).

But six concrete bugs are now reproducible via adversarial tests: multi-FK overwrite, wrapper naming collisions for _id-tables and bare id columns, type-alias autoincrement regression, stale entity files on regen, broken --with-pk-newtypes --with-serde combination, and the find_by_id universal tightening that hits every caller. Plus the self-ref junction safety gap that the per-column role-newtype design in §7 cleanly closes.

The fix plan above is ~6 commits, each small and self-contained. None require a breaking change after step 1 lands. The role-newtype work in step 6 is the highest-leverage improvement to actual safety.

The bigger design question — should we have built Id<E> instead? — is honest. For a v2 redesign, yes (with the hybrid approach in §8). For now, the per-table struct approach is workable as long as the six bugs get fixed.
